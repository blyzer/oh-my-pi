# 0070. Platform sandbox and CI: no VM-backed macOS sandbox and no Windows test job now; the existing fallbacks stand

Status: Proposed 2026-11-14; research-only, EGM round 1 resolved, round 2 pending
Date: 2026-11-14
Area: runtime

Research: [docs/research/platform-sandbox-ci.md](../research/platform-sandbox-ci.md) (Gap 19 of the upstream gap closure). This record states a research-only decision. It has no implementation slices. It states the exact events and measured thresholds that would reopen it.

## Context

### What OMPv1 does

- No VM sandbox. A search of `crates`, `docs` and `packages/coding-agent/src` of the pinned checkout for Seatbelt, `sandbox-exec`, Virtualization.framework, Tart, Lima, Firecracker, krunkit and Apple `container` found only unrelated hits. Its isolation crate `pi-iso` is copy-on-write filesystem isolation (APFS, Btrfs, ZFS, overlayfs, Linux reflink, Windows ProjFS, Windows block clone), not process confinement (`upstream:crates/pi-iso/src/apfs.rs`, `upstream:crates/pi-iso/src/overlayfs.rs`, `upstream:crates/pi-iso/src/projfs.rs`). The only VM advice is for the `computer` tool: use a dedicated account, or a dedicated VM where nobody can answer a control request (`upstream:docs/computer-use.md:6`, `upstream:docs/computer-use.md:208`). The user brings the VM.
- It does have a Vibemon client, but only for benchmark trials. `upstream:packages/metaharness/src/tb/vmon.ts` imports the Vibemon SDK (`@stencil-hq/vibemon`, line 4), boots a detached OCI image with `sandboxes.create({ image, cpus, memory, disk_mb, arch, allow_host_gateway: true, block_network: false, ... })` (`vmon.ts:201-224`), runs commands, copies files in and reads files back, attaches a host gateway with `sandbox.hostGateway(localUrl)` so the guest reaches a host-local inference endpoint (`vmon.ts:308-315`), runs the agent over a streaming exec as an RPC transport (`vmon.ts:322-331`), and removes the sandbox (`vmon.ts:333-349`). It is a harness-as-host adapter, not a sandbox for the agent's own tools. Note that these are Vibemon SDK calls: whether `allow_host_gateway` and `hostGateway` are part of the E2B API is not shown (the Vibemon README and its E2B compatibility page do not mention a host gateway; see below).
- No Windows test CI. Release binaries are cross-built on Linux, then a release-only job runs `--version` and `--smoke-test` on each platform, including `windows-2025` and `windows-11-arm` (`upstream:.github/workflows/ci.yml:863-868`, `upstream:.github/workflows/ci.yml:872-873`, `upstream:.github/workflows/ci.yml:887-889`).

### What omp2 has

- `omp-sandbox` supports Seatbelt, Bubblewrap, Landlock with seccomp, gVisor, Docker, Docker with runsc and Windows AppContainer (`crates/sandbox/README.md:3`). `Backend` is a closed enum with fixed capability sets (`crates/sandbox/src/capability.rs:22-50`, `crates/sandbox/src/capability.rs:400-423`).
- On macOS the candidates are Seatbelt, then Docker with runsc, then Docker (`crates/sandbox/src/runner.rs:1113-1116`); the fallback is Seatbelt (`crates/sandbox/src/runner.rs:1128-1135`). So a VM-bounded fallback already exists in one form: Docker Desktop and its relatives run containers in a Linux VM. The Docker backend needs an image named in `OMP_SANDBOX_DOCKER_IMAGE` and runs the command inside it with host paths only through declared bind mounts (`crates/sandbox/src/backends/docker.rs:24`, `crates/sandbox/src/backends/docker.rs:72-76`, `crates/sandbox/src/backends/docker.rs:207-208`). The command runs on Linux, not macOS. [INFERENCE: Docker Desktop on macOS runs Linux images, from general knowledge.]
- Seatbelt's launcher is `/usr/bin/sandbox-exec` (`crates/sandbox/src/backends/seatbelt.rs:21`). On the research host, macOS 27.2.1, `man sandbox-exec` reads "sandbox-exec – execute within a sandbox (DEPRECATED)". It is deprecated, not removed. Apple's own account of why: an Apple Developer Technical Support engineer wrote in September 2020 that the sandbox specification language "is not documented for third-party use. This, btw, is why sandbox-exec has been deprecated" (<https://developer.apple.com/forums/thread/661939>, fetched 2026-11-14). So it has been deprecated for at least six years and is still present. Seatbelt has no IPC restriction, no `proc.noexec` and no CPU, memory or process limits (`crates/sandbox/src/capability.rs:320-332`), and records its own caveats: path-based scopes that an allowed hardlink can bypass, ephemeral writes as an APFS clone of the working directory, no disk limit, loopback blocked with network off (`crates/sandbox/src/backends/seatbelt.rs:325-398`).
- **A removal detector already exists in code and CI.** `seatbelt::probe()` runs `/usr/bin/sandbox-exec -p "(version 1) (allow default)" /usr/bin/true` and returns `ProbeFailure::Start` if the launcher cannot be started (missing binary) or `ProbeFailure::Rejected` with the exit status and up to 4096 bytes of stderr if it runs and fails (`crates/sandbox/src/backends/seatbelt.rs:436-473`). Proof P12 fails, rather than skips, on macOS when that probe fails (its doc comment: "a failed Seatbelt probe is an error naming the failure, never a skip": `crates/e2e/tests/p12_daemon_approvals.rs:13-14`, `crates/e2e/tests/p12_daemon_approvals.rs:63-72`), and P12 gates in the macOS CI job (`AGENTS.md`, CI section). So the day a GitHub-hosted or self-hosted macOS image no longer ships a working `sandbox-exec`, CI goes red with the named failure. What is missing is a rule for what that red result reopens.
- ADR 0006 puts a VM at the environment-target level: "The same host MUST be able to point the stub at a local process, a container, a VM, or a remote machine"; today every target runs the full `omp-envd`, and a minimized stub is deferred (`docs/adr/0006-host-policy-sandbox-stub.md:44-47`, `docs/adr/0006-host-policy-sandbox-stub.md:150`). A guest with an SSH server is reachable by the SSH execution backend for build and test commands (`crates/exec-ssh/README.md:1-6`); whether general tools can target an SSH host was not traced (UNVERIFIED).
- VM tool terms, read from the GitHub API on 2026-11-13: Tart is under the Functional Source License (FSL-1.1-ALv2, copyright line naming OpenAI in the file), and its "Competing Use" clause bars making the software available in a commercial product that substitutes for it or offers substantially similar functionality, while internal use is permitted. Lima, Apple `container`, Apple `containerization` and UTM are Apache-2.0; Colima is MIT. Apple `container` runs Linux containers as lightweight VMs, needs Apple silicon and is designed for macOS 26 or later (its README).

### The MicroVM route: ADR 0052 and ADR 0007

- ADR 0052's implementation guide proposes one generic MicroVM capability behind the execution contract, with an E2B/Vibemon adapter first (`docs/adr/0052-one-executor-contract.md:40-67`). The contract it would implement is `ExecutionBackend` (`start`, `reattach`) and `ExecutionRun` (`next_event`, `cancel`, `detach`) (`crates/exec/src/backend.rs:139-177`). `ExecutionRequest` carries `argv`, `cwd`, an environment allowlist, an input set and an output spec (`crates/exec/src/request.rs:157-182`), and the crate documents itself as the build-and-test execution domain (`crates/exec/src/lib.rs:1`). Placement defaults to local only: `FallbackPolicy` is `LocalOnly` by default (`crates/exec/src/backend.rs:70-77`). Vendor backends are extensions behind the in-core `Delegated` adapter (`docs/adr/0040-remote-build-and-test-execution.md:1833`; `docs/adr/0049-tiered-integration-architecture.md`, D1 tier table: all vendor integrations are T2).
- What Vibemon says about itself (<https://github.com/stencil-hq/vibemon>, fetched 2026-11-14): a self-hosted microVM platform that speaks the E2B API, with the E2B SDKs and CLI working unmodified; sandboxes are copy-on-write forks of a template snapshot with no kernel boot; pause writes a memory delta and a disk overlay; MIT licence with Apache-2.0 for E2B-derived parts. Platform table: Linux/KVM guests x86_64 and aarch64 (VMM, node and driver roles); macOS 15+/HVF guest aarch64 (VMM, node and driver roles); Windows/WHP guest x86_64 (VMM only). macOS binaries must be ad-hoc signed with `hvf.entitlements`; Linux nodes need `/dev/kvm`, and TAP networking needs root or `CAP_NET_ADMIN`. The README gives no start-latency figure and no benchmark.
- What its compatibility page says (<https://github.com/stencil-hq/vibemon/blob/main/docs/src/reference/e2b-compat.md>, fetched 2026-11-14): sandbox create, list, kill, timeout, connect, pause, fork, snapshot-as-template and template operations are routed; the envd process service (Start, Connect to reattach, SendInput, SendSignal) and filesystem service and `/files` upload and download are implemented over Connect v1; paused sandboxes auto-resume on connect. Limits that matter here: egress header `rules` are Linux-only and "currently failing in the macOS test run"; on macOS the egress filter admits only domains on TCP 80 and 443; **"Not yet run: Linux/KVM end-to-end testing"**; GPU sandboxes lose memory on resume. Its test status is Python SDK 1444 passed, 8 failed, 34 skipped and JS SDK 1007 passed, 1 failed, 36 skipped. The guests are Linux (its init list names Debian, Ubuntu, RHEL, Arch and Alpine). So Vibemon on an Apple-silicon Mac is a Linux VM boundary, the same kind of boundary Docker Desktop gives today, not a macOS-native sandbox.
- What E2B documents (<https://docs.e2b.dev/sandbox/persistence.md>, <https://docs.e2b.dev/sandbox.md>, fetched 2026-11-14): `Sandbox.create()` with a timeout; `commands.run`; pause saves filesystem and memory, "pausing takes about 4 seconds per 1 GiB of RAM" and "resuming takes about 1 second"; `Sandbox.connect()` resumes a paused sandbox; paused sandboxes are kept until killed; network connections drop on pause. The documentation does not state a cold-start time.
- **Gap between the reference adapter and the E2B API.** `vmon.ts` boots from an OCI `image` and uses `allow_host_gateway` and `hostGateway` (`upstream:packages/metaharness/src/tb/vmon.ts:201-224`, `upstream:packages/metaharness/src/tb/vmon.ts:308-315`). The E2B-shaped path boots from a template and has no host-gateway call in the pages fetched. So an adapter restricted to the E2B API cannot assume the inference gateway that ADR 0052 D8 and ADR 0039 K2 rely on; either the guest reaches inference through an allowed egress route with no key in the guest, or the adapter uses a Vibemon-specific call and stops being "E2B-API only". UNVERIFIED which of the two Vibemon supports; it is a V0 test (X8 below).
- For subagent isolation, ADR 0007's rule is a per-writer view, no write access to the parent tree, and a content-addressed patch or branch returned, with the base manifest digest recorded (`docs/adr/0007-subagent-filesystem-isolation.md`, Decision and Amendment 2026-11-12). Today the view is built by `create_worktree`, which clones each manifest entry with `clone_file_cow` (`crates/envd/src/workspace/operations.rs:673-725`, `crates/envd/src/workspace/operations.rs:2041`), proven by `crates/e2e/tests/p9_isolation.rs`. The wire message that asks for a view has no backend field: `CreateWorktree { name, base, paths, owner_pid, props }` (`crates/proto/proto/omp/env/v1/env.proto:1154-1160`), and `SCHEMA_REV` is 29 (`crates/proto/src/lib.rs:51`). A VM-backed view therefore cannot be selected through the existing message without a new field.

### Windows

- Code exists in 19 crates under `cfg(windows)`, including an AppContainer sandbox backend and a `win32` desktop backend (`crates/sandbox/src/backends/appcontainer.rs`, `crates/desktop/src/win32`, `Cargo.toml:325`). There is no Windows CI job; the workflows are Ubuntu and macOS only (`.github/workflows/p8-baseline.yml:50-56`). A whole-workspace Windows build is blocked: `omp-py` is an ungated dependency of `omp-app` and `omp-envd` (`crates/app/Cargo.toml:103`, `crates/envd/Cargo.toml:67`), and its fetch script supports only macOS arm64 and Linux x86_64 and aarch64 (`crates/py/scripts/fetch-python.sh:153-168`), with link lists for ELF and Mach-O only. The `justfile` uses `bash` (`justfile:5`) and the toolchain is a pinned nightly (`rust-toolchain.toml:2`).
- How much Windows-gated code is changing, measured at `9cb6fd6389` on 2026-11-14 with `git log -G'cfg\(windows\)|target_os = "windows"'` over `crates`: 109 Rust files contain such a cfg; 65 commits since 2026-08-14 (the history begins 2026-08-08) add or remove a line carrying one; 3 of those fall in the last 30 days. The AppContainer backend file was last changed 2026-09-04 (`de7a1c71a9`). So the change rate that rots unchecked Windows code is falling, which is the evidence for not paying for a job now, and the 30-day count is the number that the Windows trigger below watches.
- CI economics: the self-hosted Mac runs the one job that benefits from its persistent target directory; everything else is hosted (`docs/research/ci-macos-runner-fallback.md:5-21`). Ten named checks are required and new jobs must not rename them (`docs/BRANCH_PROTECTION.md:42`, `docs/BRANCH_PROTECTION.md:84`).

### Rules that bind

- ADR 0006: policy on the host, an obedient stub in the sandbox; a VM is an environment target.
- ADR 0036: Python-only extensions and eval, which is why embedded Python cannot simply be made optional. ADR 0024: no new roster family. ADR 0049: vendor integrations are extensions. Additive only: `CreateWorktree`, the `Backend` enum and `SCHEMA_REV` are existing surfaces.
- No new language runtimes; no `pi` identity.

## Decision

**D1. Do not add a VM-backed macOS sandbox backend now.** Seatbelt stays the macOS default. The Docker forms stay the fallbacks. Reasons: `sandbox-exec` is deprecated but present and its removal is already detected by a probe and a failing proof (see Context); a Linux VM boundary already exists through Docker; a macOS-guest design needs an entitlement, an image distribution story, host-side egress filtering and a shared-directory story, none of which has been measured; and ADR 0006 places a VM at the environment-target level, not in the sandbox crate.

**D2. Do not bundle or redistribute Tart.** Its licence limits making it available in a competing product. Any documented recipe names Apache-2.0 tools (Lima, Apple `container`) first and treats Tart as an optional user-installed tool, pending the owner's view (O4).

**D3. Do not build a MicroVM execution backend or a VM subagent-isolation backend now.** Neither is built from this record. If either is ever built, the shape is fixed here so the work does not drift: a T2 extension behind the in-core `Delegated` execution adapter (ADR 0052 D8, ADR 0049 D1), implementing the minimum contract of ADR 0052's guide, not a new `Backend` variant in `omp-sandbox`. It reaches subagent isolation only through the thresholds in D6 and an owner ruling on the wire question (O9).

**D4. Reopen triggers.** This record is reopened, and a new record with slices is written, only when one of the following named events occurs. Each is checkable without judgment.

*Trigger S (Apple signal for `sandbox-exec`).* Any one of:
- S1. `just e2e-p12` or the `Rust workspace and acceptance proofs` job goes red on macOS with `ProbeFailure::Start` (launcher missing) or `ProbeFailure::Rejected` from `seatbelt::probe()` (`crates/sandbox/src/backends/seatbelt.rs:436-473`), on any macOS image, including a beta image run by hand.
- S2. A macOS release's notes or the `sandbox-exec` man page change from "DEPRECATED" to stating removal, or Apple developer documentation names `sandbox-exec` or the `<sandbox.h>` API as removed. Check at each macOS major release; today's baseline text is "DEPRECATED" (research host, macOS 27.2.1).
- S3. Apple documents a supported way for a command-line tool to confine a child process. That reopens the question in the other direction (a supported API may replace Seatbelt without a VM).
Effect of S1 or S2: macOS candidates fall to the two Docker forms (`crates/sandbox/src/runner.rs:1113-1116`), which need an image. Reopen to decide between a documented Linux-VM recipe and the MicroVM route; the preferred shape stays D3.

*Trigger H (owner need).* The owner records a use case where closing Seatbelt's hardlink-style scope bypass or its missing CPU, memory and process limits (`crates/sandbox/src/capability.rs:320-332`, `crates/sandbox/src/backends/seatbelt.rs:325-398`) is required. Without such a ruling the Docker forms already offer those limits.

*Trigger V (measured MicroVM thresholds).* The V0 spike in Slices passes every gate in D5 on both Linux and Apple silicon. Passing is required for any MicroVM backend; it is not by itself a reason to build one. A build also needs S1, S2 or H, or the isolation need of D6.

**D5. V0 thresholds for a MicroVM execution backend (ADR 0052) tested against Vibemon.** The numbers are this record's proposals [INFERENCE], to be ratified or replaced by the owner (O9). A run is on one Linux host with `/dev/kvm` and one Apple-silicon Mac on macOS 15 or later, both running the same Vibemon commit, both from a warm template. "p95" means the 95th percentile of at least 30 sequential runs.

| Gate | Measure | Threshold | Why this number |
|---|---|---|---|
| X1 conformance | The adapter's calls pass on both hosts: create from template, envd process Start, Connect, SendInput, SendSignal, stream to exit; `/files` upload and download; kill; pause then connect | 100% of the adapter's calls, 0 failures in 30 runs | Vibemon records Linux/KVM end-to-end testing as "Not yet run" in its compat page, so Linux is a real gate, not a formality |
| X2 start | Create from a warm template to first `true` returning exit code 0 | p95 at most 2.0 s | Twice E2B's documented resume of about 1 s; neither E2B nor Vibemon documents a cold start |
| X3 exec overhead | `true` in an existing sandbox, wall time minus the same command through `omp-exec-local` on the same host | p95 at most 250 ms | A build or test step is seconds to minutes; per-call overhead above this makes many small calls visibly slower |
| X4 workspace in | Copy this repository's non-ignored manifest into the guest (the set `create_worktree` snapshots) | p95 at most 30 s, and recorded next to B0 | Must stay in the range of the existing copy fallback (ADR 0007 Consequences) |
| X5 cancel and kill | `ExecutionRun::cancel` until the guest process is gone; sandbox kill until resources are released | at most 5 s and 10 s | `cancel` is the one cancel path (`crates/exec/src/backend.rs:168-173`) |
| X6 reattach | Detach, drop the client, reattach through process Connect, read remaining output and the exit code | 0 lost or duplicated results in 20 trials | `reattach` and `detach` exist for this (`crates/exec/src/backend.rs:156`, `:177`); ADR 0052 safeguard 3 forbids relaunching blindly |
| X7 egress | `block_network` deny-all holds on both hosts; the adapter declares its enforced posture honestly | deny-all passes 20 of 20; any scoped-allow need on macOS is declared as unsupported (the compat page admits only domains on TCP 80/443 there) | ADR 0052 D2 and D9: advertised is not enforced |
| X8 inference path | A guest turn completes against a host-side inference endpoint with the provider credential absent from the guest | 0 matches for the credential in the guest environment and filesystem; the route used (egress allowlist or a Vibemon-specific gateway) is recorded | The `vmon.ts` gateway is a Vibemon SDK call, not shown to be E2B API |
| X9 density | Concurrent sandboxes on a 16 GiB host, for the parallel isolation of ADR 0007's amendment | 8 concurrent, 0 failures in 10 rounds; idle memory per sandbox recorded | Parallel phases are roadmap P3 |

Baseline B0, measured first and on the same hosts: `create_worktree` time on this repository's manifest on the reflink path and on the forced copy path, and `omp-exec-local` `true` latency. B0 has no stored number today (UNVERIFIED); every relative claim waits for it.

**D6. Thresholds for a VM as a subagent isolation backend (ADR 0007).** In addition to D5, all of:
- I1 (rule). A guest edit never appears in the host tree: the host manifest digest before and after is identical in 20 of 20 runs, and a patch returned from the guest applies to the host view and yields the same digest as the reflink path for the same edits on the P9 fixture (`crates/e2e/tests/p9_isolation.rs`). The base manifest digest is recorded with the patch.
- I2 (cost). Materialize the repository manifest in the guest and return the patch at most 3 times B0's reflink path and at most 30 s absolute.
- I3 (need). At least one of: a use case with process or network confinement of a child beyond the filesystem view that `omp-sandbox` cannot supply, ratified by the owner; or a copy-fallback `create_worktree` of this repository's manifest above 30 s (p95) on a filesystem without copy-on-write that the owner names as supported. Without I3 the reflink view is faster and already satisfies ADR 0007.
- I4 (wire). The owner rules on how a VM view is requested (O9): an additive `CreateWorktree` field is a schema change (`SCHEMA_REV` 29) and so is not designed around here.

**D7. Windows CI triggers.** Do not add a Windows test job now. The staged route stays: (a) list the crates that do not depend on `omp-py` for a Windows target, (b) a non-required compile check of those crates, switched on by a repository variable and run on demand and nightly, (c) their unit tests on a hosted Windows runner, (d) only on an owner decision, embedded Python for Windows and a release smoke like upstream's. Stage (b) starts when any one of these events occurs:
- WIN1. The owner decides a Windows binary will ship (O7). Then (a) and (b) start, and (d) is planned in its own record.
- WIN2. Windows-gated code starts moving again: 5 or more commits in any rolling 30 days whose diff adds or removes a line matching `cfg(windows)` or `target_os = "windows"` under `crates` (today: 3 in 30 days, 65 in 90 days; command in Context), or any commit that changes `crates/sandbox/src/backends/appcontainer.rs` or `crates/sandbox/src/runtime/windows.rs`, because a sandbox backend cannot be reviewed without a build.
- WIN3. A user report or issue whose cause is in `cfg(windows)` code.
- WIN4. `crates/py/scripts/fetch-python.sh` gains a Windows archive. A whole-workspace job (stages (c) and (d)) is then reconsidered.
Stage (c) needs, besides one of these, the measured cost of one run (O8).

**D8. Gating of any later work.** This record changes no convar, feature or CI file. Later work is default-off: a `cap-sandbox-vm` feature with a default-off `sv_sandbox_vm` convar for VM work in core crates; a MicroVM backend extension is opt-in by installation and only receives work when the operator moves `sv_exec_policy` off its `local-only` default (`crates/exec/src/backend.rs:70-77`); Windows CI is gated by a `vars.CI_WINDOWS` repository variable, unset by default.

## Rejected options

- **A new `Backend::VmGuest` variant now.** Weeks of work and an entitlement, with no measurement showing the need. It also touches every exhaustive `match` on `Backend` (`crates/sandbox/src/runner.rs:41`, `crates/sandbox/src/runner.rs:240`, `crates/sandbox/src/runner.rs:318`, `crates/sandbox/src/runner.rs:406`, `crates/sandbox/src/runner.rs:458`).
- **A Vibemon or E2B adapter in a core crate.** Vendor integrations are extensions (ADR 0049); core stays vendor-neutral.
- **Treat a Linux microVM on macOS as a replacement for Seatbelt.** Vibemon guests are Linux, so a macOS-native command does not run in them; the boundary equals what Docker Desktop already gives.
- **Bundle Tart or any VM tool.** No redistribution right for Tart; the others are not needed to decide.
- **A full-workspace `windows-latest` job.** Blocked by `omp-py`.
- **Add Windows support to `omp-py` now.** Large, and it widens a locked area (ADR 0036); only with an owner decision for a Windows release.
- **Vague triggers ("when Apple removes it", "when VMs are fast enough").** Round 1 rejected them; D4 to D7 replace them.
- **Do nothing and say nothing.** The Seatbelt deprecation and the missing Windows check deserve a recorded decision and triggers.

## Slices

None. This record is research only and authorizes no implementation. Its work items are measurements with no repository change; each produces a table in a research note, not code.

- **B0 (baseline spike).** Measure `create_worktree` (reflink and forced copy) on this repository's manifest and `omp-exec-local` `true` latency on the self-hosted Mac and a Linux host. Needed by D5 X3, X4 and D6 I2, I3.
- **V0 (spike).** Run D5 on Linux/KVM and Apple silicon against one pinned Vibemon commit using E2B's own client calls, and write the table. Add D6 only if I3 has a ratified need. Also time a clean Lima and Apple `container` guest start for the Linux-VM recipe comparison; Tart only as a user-installed tool (O4). Until measured, every VM speed claim is UNVERIFIED.
- **W0 (list).** List the workspace crates that do not depend on `omp-py` for a Windows target, using the dependency graph. Until listed, the claim that a subset can build on Windows is UNVERIFIED.

If a trigger fires and the owner accepts, each stage gets its own record with slices, acceptance tests and, where it applies, an e2e proof in `crates/e2e` and a golden journal.

## Upstream origin and license

Nothing from upstream is reused: it has no VM sandbox, and its Vibemon client (`vmon.ts`) is a TypeScript benchmark harness that is only a reference for the lifecycle (create, exec, copy in, read file, gateway, remove). For Windows CI the useful idea is the release smoke matrix and the comment explaining why binaries are cross-built and then run on their own platform (`upstream:.github/workflows/ci.yml:863-868`). Upstream's `LICENSE` is MIT (copyright Mario Zechner, Can Bölük, Stencil Labs, Inc.; `upstream:LICENSE:1-5`); workflow YAML is configuration and copying it keeps that notice. Third-party tools were checked only for licence: Tart FSL-1.1-ALv2; Lima, Apple `container`, Apple `containerization` and UTM Apache-2.0; Colima MIT; Vibemon MIT with Apache-2.0 for E2B-derived parts (its README, 2026-11-14).

## Consequences

- macOS sandboxing is unchanged: Seatbelt with its documented caveats, Docker as the Linux fallback.
- The `sandbox-exec` deprecation is tied to a signal that already exists (probe plus P12) and to three named Apple events, so a removal is not a surprise and does not need a new watcher.
- The MicroVM route has numbers to pass before anyone builds it, and a stated place in the architecture.
- Windows code stays unchecked in CI. `cfg(windows)` paths can rot unseen until a D7 event occurs; the current change rate is low (3 commits in 30 days).
- Nothing in the repository, its CI or its dependencies changes.

## Open questions for the owner

- **O1.** Apple's macOS licence for guests: how many macOS guests a Mac may run, and under what terms. Not read (UNVERIFIED). Recommendation: read it before any macOS-guest work.
- **O2.** Nested virtualization: GitHub-hosted macOS runners are VMs themselves; whether Virtualization.framework or HVF runs inside them is unknown. Recommendation: assume VM work is testable only on the self-hosted Mac and a Linux host with `/dev/kvm`.
- **O3.** Entitlements and signing for Virtualization.framework use. Vibemon's macOS binaries need an ad-hoc signature with `hvf.entitlements` (its README); omp's signing was not checked. Recommendation: check against `package-macos.yml` before any VM backend.
- **O4.** Is a recipe that names Tart acceptable, given its FSL licence and Competing Use clause? Recommendation: name Lima and Apple `container` first; mention Tart only as a user-installed option, or not at all.
- **O5.** Seatbelt's removal date. None found. Recommendation: the D4 trigger S stands until Apple states one.
- **O6.** Can general tools, not only build runs, target an SSH host? Not traced. Recommendation: trace it before writing any guest-over-SSH recipe.
- **O7.** Does the owner want a Windows release? Recommendation: decide before spending on `omp-py` for Windows; until then take D7 stages (a) and (b) only if cheap.
