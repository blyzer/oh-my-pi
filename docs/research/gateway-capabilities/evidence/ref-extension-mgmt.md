> Part of the [OMP2 gateway-capabilities research](../README.md). Evidence file for deliverable 7. ## 1. router-for-me/CLIProxyAPI @ dbe641f (MIT)

Read: code (Go) for the plugin host, store and ABI types, plus the plugin examples README and `config.example.yaml`.

**Mechanism (X01).** A plugin is a native dynamic library (`c-shared`) loaded in the host process. The host calls `dlopen(path, RTLD_NOW | RTLD_LOCAL)`, resolves the single symbol `cliproxy_plugin_init`, and exchanges two C structs: `cliproxy_host_api` (host callbacks) and `cliproxy_plugin_api` (`call(method, request_bytes, len, out_buffer)`, `free_buffer`, `shutdown`), each carrying `abi_version` (`router-for-me/CLIProxyAPI@dbe641f:internal/pluginhost/loader_unix.go:22-39, 44-49, 194-214`). The calls carry serialized JSON, so the ABI is a thin C shell around a message protocol: "native dynamic library plugins communicate across the C ABI via serialized JSON buffers" (`examples/plugin/README.md:131`). Methods are named strings such as `plugin.register`, `plugin.quiesce`, `plugin.reconfigure`, `plugin.shutdown`, `model.register`, `auth.login.start`, `scheduler.pick`, `model.route`, `executor.execute`, `executor.execute_stream`, `request.translate`, `response.intercept_stream_chunk`, `thinking.apply`, `usage.handle`, `quota.fetch`, `management.register`, `host.http.do` (`sdk/pluginabi/types.go:79-144`). `ABIVersion uint32 = 1` (`sdk/pluginabi/types.go:10-11`). Examples exist in Go, C and Rust (`examples/plugin/README.md:30`).

**Costs of the in-process C ABI, as stated by the code.**
- A Go `c-shared` runtime cannot be unloaded: after `dlopen`, "the image must never be unloaded", failure paths "deliberately leak the mapped image" (`internal/pluginhost/loader_unix.go:188-192`). Independent termination is therefore not available.
- The host re-executes its own binary with `CLIPROXY_PLUGIN_DLOPEN_PROBE` to probe whether a library loads, because a bad library can crash the process (`loader_unix.go:133-160`; `internal/pluginhost/shadow.go`, 616 lines, copies the library to a shadow path before loading).
- Prebuilt artifacts must pin the CPU baseline so instructions compiled on a CI runner do not fault on other machines (`examples/plugin/README.md:175-178`).
- Error semantics must be encoded inside the JSON envelope (`http_status`) because only bytes cross (`README.md:118-131`).

**Capability surface (X02).** Capabilities are declared at runtime by the plugin (`plugin.register`), not in a static signed manifest. A store manifest carries metadata only (id, name, author, version, release tag, repository, licence, tags, locales, install plan; `internal/pluginstore/manifest.go:9-27`). This is a runtime-asserted surface, in contrast to OMP2's static declaration table.

**Registry and distribution (X03, X09).** JSON registry `{schema_version, plugins[]}`; each plugin has `versions[]` and an `install` plan of per-`goos`/`goarch` artifacts `{url, sha256, size}` (`internal/pluginstore/registry.go:36-83`). Default registry is a raw GitHub URL for `router-for-me/CLIProxyAPI-Plugins-Store` (`registry.go:17`); extra `store-sources` and per-URL store authentication by environment variable are configurable (`config.example.yaml:1415-1445`). Install types: direct artifacts and GitHub release (`manifest.go:46-61`).

**Integrity (X04).** SHA-256 only: `VerifyChecksum` and `VerifyArtifactChecksum` (`internal/pluginstore/checksum.go:34`, `direct.go:45`, `install.go:133, 169`). A case-insensitive search of `internal/pluginstore` and `internal/pluginhost` for `ed25519|cosign|minisign|gpg|signature|verify` found only checksum helpers. No publisher signature, key pinning or revocation was found.

**Permissions and isolation (X05).** None beyond an enable flag: `plugins.enabled: false` by default and per-plugin `enabled` and `priority` (`config.example.yaml:1415-1416, 1450-1455`). The plugin runs with the host's privileges in the host address space.

**Upgrade (X08).** Atomic replace of the library file (`install.go:299, 519-566`); the registry may list several versions. No rollback or generation retention was found (`rg` for rollback, backup, previous in `pluginstore`).

**Dependencies and compatibility (X10, X11).** No dependency field in `Plugin` or `Manifest` (structs read). Compatibility is the integer `abi_version` checked by the host and `schema_version` of the registry.

**Health (X07).** Not examined in this pass.

**Lesson for OMP2.** The useful parts are the registry shape (per-platform artifact table), store authentication by environment-variable reference (the secret never enters a manifest), the stable method-name vocabulary over a message payload, and the `quiesce`/`reconfigure` lifecycle verbs. The costs (no unload, probe-by-reexec, CPU-baseline pinning, no signatures, in-process privileges) are the reasons the owner excluded the C ABI route. OMP2 already has the safer variants of each useful part (section 5 of `omp2-extensions.md`).

## 2. Ve-ria/CLIProxyAPIPlus @ 60bb379 (AGPL-3.0; ideas only, nothing copied)

- **Everything else (registry, signatures, permissions, health, rollback, dependencies, compatibility):** not present in the code read; marked `N` where a search covered it and `U` where it did not.
- **Lesson.** The "Plus" fork stayed on static registration plus config; the dynamic-library host appears only in the upstream repository at a later head. This supports the position that a gateway can grow a large provider set without a plugin ABI.

## 3. stark-shadow/ecpa-plugins-store @ 2d82289 (no licence file; ideas only)

Read: `README.md` and `registry.json` in full (2 tracked files). Code: none; the repository is data plus a maintenance policy.

- **What it is (X03).** A hand-maintained curated plugin registry for the CLIProxyAPI plugin store protocol. `registry.json` has `schema_version: 2` and 17 plugin entries (`stark-shadow/ecpa-plugins-store@2d82289:registry.json`). It "follows the same format and release contract" as `router-for-me/CLIProxyAPI-Plugins-Store` so entries can move between stores (`README.md`, first paragraph). A client adds it as an extra `store-sources` URL; the built-in official source is always included (`README.md`, "Consuming the registry"), matching `router-for-me/CLIProxyAPI@dbe641f:config.example.yaml:1418-1420`.
- **Metadata only.** Entries carry id, name, description, author, version, repository, logo, homepage, licence, tags and locales. The README states: "Do not add `install`, `artifacts`, `source_id` or download URLs. Installation metadata is derived from the plugin's own GitHub releases". Across the 17 entries a count from the JSON shows 14 with `install.type = "github-release"`, 3 with no `install`, and no entry with an `artifacts` array or a hash.
- **Release contract (X09, X04).** The latest GitHub release must carry one `checksums.txt` (`sha256sum` format) and one zip per platform named `<id>_<version>_<goos>_<goarch>.zip`; each zip holds exactly one dynamic library at its root (`<id>.dylib`, `.so`, `.dll`); the installer rejects nested libraries, absolute paths, zip-slip paths, mismatched names and multiple libraries (`README.md`, "Release Requirements" and "Zip Layout"). Integrity is therefore SHA-256 from the same release as the artifact; no publisher signature or key pinning is described. The checksum shares a trust root with the artifact, so it detects corruption, not a compromised release.
- **Validation rules (X02, X11).** `id` grammar and uniqueness, `repository` must be exactly `https://github.com/{owner}/{repo}`, `version` must not start with `v`; `schema_version` 2 is required once any entry states `install` (`README.md`, "Validation Rules").
- **Operations.** Maintained by hand ("not a mirror of anyone else's store"); a wholesale copy once deleted two entries (`aistudio2api`, `freetier`, `aea2464`, 2026-11-09, per the README). A timer queries each entry's `releases/latest` twice an hour to sync versions (`README.md`, "Automated Version Sync"). Single-maintainer, unsigned index, mutable by anyone with push access: the opposite trust model from OMP2's signed index with an expiry window and TOFU pins (`crates/ext/src/index.rs:235-351`).
- **Registry content and provider terms.** Entry descriptions (read in `registry.json`) include plugins that "turn free-tier quotas from 15 AI coding assistants ... into OpenAI, Responses and Anthropic APIs ... check-in and cross-provider load balancing" (`freetier`), a plugin with "multi-account cooldown-aware scheduling" built on an in-process BotGuard engine (`aistudio2api`), an "unofficial" provider with desktop session import (`doujie-oauth`), and shared model pools with daily check-ins (`freecredits2api`). Only the descriptions were read; no plugin was inspected. Under method rule 8, any such capability that exists to defeat usage limits, pool one subscription across other people, or use a private API a provider has not authorised is classified `Rejected for security, licensing or operational reasons` for OMP2. The registry mechanism itself is not rejected. Credential-health inspection and detection-only grouping (`cpa-gpt-risk-group-plugin`) is a different case, and was not examined.
- **Lesson for OMP2.** A store can be pure data pointing at publisher-owned releases, which keeps the registry tiny but pushes all trust to a mutable GitHub release. OMP2's index copies the artifact hash and signature into a signed snapshot, which is the stronger design and already implemented. A "curated community index" for OMP2 would be an index with a different signing key, configured through `omp ext index` (`crates/app/src/ext_cli/mod.rs:279-340`).

## 4. lzt404/EasyCLIProxyAPI @ faf29b2 (MIT)

Read: README opening, directory listing, selected Rust modules by symbol and string search (`src-tauri/src/core_runtime.rs`, `provider_health.rs`, `core_config/settings.rs`, `agents/discovery.rs`). Not a plugin system.

- **What it is.** A Tauri (Rust) and React desktop console that manages a CLIProxyAPI core as a child process: start, stop, restart (`lzt404/EasyCLIProxyAPI@faf29b2:src-tauri/src/core_runtime.rs:434-471`), terminate child (`:2358`), plus YAML configuration editing (`src-tauri/src/core_config/`), a management-API client, a configuration watcher and an instance lock. The core version is pinned in `core-version.txt` (8.0.6) and a matching core archive can be bundled for offline install (README, "Overview").
- **Integrity (X04).** Bundled kernel archives are verified against a checksum file (`core_runtime.rs:617-618 validate_bundled_core_checksum`), and downloads against an expected SHA-256 digest (`:979-985`, `:1203-1228`). No signature check was found in `core_runtime.rs` or `app_update.rs` by string search for `signature|minisign|verify`.
- **Plugins.** Configuration only: a `plugins.enabled` boolean mirrored into the core YAML (`core_config/settings.rs:612-614`). The word "plugin" elsewhere refers to configuring other agent CLIs (for example a Pi provider plugin setting, `agents/discovery.rs:341-400`). A string search of `src`, `src-tauri/src` and the README for `plugin store`, `store-sources` and `registry.json` found nothing, so any "Plugin Store" tab named in the store's README is documentation-only evidence here.
- **Health (X07).** Provider health probes: a bounded concurrency of 4 and a 256 KiB stream cap (`provider_health.rs:12-13`); core status is returned by the lifecycle commands.
- **Lesson for OMP2.** This is an example of the "external integration" pattern: a typed Rust supervisor owns the gateway as a child process, pins and verifies its version, and edits its configuration. It supports EXT-08 (external process behind a declared endpoint) and the existing `Delegated` shape, and it shows what an OMP2 front end would need to manage a locally run gateway (start, stop, pinned version, configuration patching, health probe). It does not need a plugin ABI.

## 5. Ve-ria/quickx @ e13db37 (GPL-3.0; study only, nothing copied)

Read: README, `src/lib/templates.ts` (symbol and string search plus lines 12-95), `src/lib/store.ts` and `src/lib/codex.ts` by string search. TypeScript, Ink TUI. `AmethystDev-Labs/QuickCLI`, which this tool names as its template registry, is unavailable (404), so the registry side is known only from this client's URLs.

- **What it is.** A Codex profile manager: stores several provider configurations and writes the active one to `~/.codex/config.toml` (README, opening; `Ve-ria/quickx@e13db37:src/lib/codex.ts:108-112`).
- **Declarative provider templates (X01, X02).** A template is data: `id`, `displayName`, `scope`, `baseUrl`, `apiKey`, `model`, `wireApi` (`responses` or `chat`), `authMethod` (`api_key` or `chatgpt`), `docsUrl`, `requiredEnvs`, reasoning fields and an optional `codexTomlContent` fragment. Values may contain prompt placeholders of the form `${--:"label":"default"}` (`src/lib/templates.ts:20, 27-94`). Built-in presets cover OpenAI, Azure OpenAI, Ollama and LM Studio. This is the same idea as OMP2's provider rows in `extensions/provider-pack/omp.toml` and the catalog, but without a schema revision, capabilities or signatures.
- **Registry (X03).** Remote templates come from `AmethystDev-Labs/QuickCLI`, branch `main`, path `templates/<id>/template.yaml`, listed through the GitHub contents API and fetched from `raw.githubusercontent.com`, then merged with the built-ins and cached for one hour (`templates.ts:14-19, 96-101, 172-193, 239-248, 288-290`).
- **Integrity (X04).** A string search of `templates.ts` for `sha|hash|signature|integrity` found no verification. Templates, including an injectable TOML fragment, come over HTTPS from a mutable branch with no pinning, so a repository compromise changes what a user writes into their Codex configuration.
- **Secrets.** API keys are stored in plaintext in the profile JSON (`src/lib/store.ts:29, 66`), written atomically with mode `0600` in a `0700` directory (`store.ts:109-113`). OMP2 instead keeps credentials behind references and host placement (ADR 0075).
- **Lesson for OMP2.** Confirms that a provider "template" is a data row plus user-supplied slots, and that the weak points of such a registry are unsigned mutable sources and secrets in the profile. OMP2's provider rows, signed index and credential grants already address both. The useful UX idea is "preview what a template needs" (`quickx templates preview`), which maps onto `omp ext info --capabilities`.

## 6. hashicorp/go-plugin @ 415e29b (MPL-2.0)

Read: `README.md`, `docs/internals.md`, `client.go` (handshake, checksum, kill, versioned plugins), `grpc_server.go`, `grpc_client.go`, `protocol.go`. Go library, not a registry. Reference point for the "independently executable plugin over messages" option.

- **Mechanism (X01).** Out-of-process plugins: the host launches a plugin binary as a subprocess; the plugin prints a one-line handshake on stdout and serves RPC on a local control address; the host connects and dispenses plugin interfaces (`docs/internals.md`, "Internals" steps for server and client). Protocols: `netrpc` (default, Go only) and `grpc` (`hashicorp/go-plugin@415e29b:protocol.go:16-17`, `client.go:413-414`). Plugins "can be written (and consumed) by almost every major language" through gRPC (`README.md:28-31`; `docs/guide-plugin-write-non-go.md`). There is no shared library and no in-process call (compare section 1).
- **Handshake and versioning (X11).** The stdout line is parsed as `|`-separated fields; the first is the core protocol version, which must equal `CoreProtocolVersion` or the host refuses with "incompatible core API version" (`client.go:834-868`). The second field is the application protocol version, negotiated against `VersionedPlugins map[int]PluginSet` so a host can serve several plugin interface versions at once (`client.go:150-153, 619-634`, `checkProtoVersion` at `:871`). A "magic cookie" environment variable is passed to the plugin as a guard against running the binary by hand; the tutorial states "It is a UX feature, not a security feature" (`docs/extensive-go-plugin-tutorial.md:75`; cookie env at `client.go:639`).
- **Integrity (X04).** Optional `SecureConfig{Checksum}`: the host hashes the plugin binary and compares in constant time before executing it, returning `ErrChecksumsDoNotMatch` (`client.go:51-57, 327-356, 665`). The library has no signature or registry; the checksum's source and trust are the embedding application's problem.
- **Permissions and isolation (X05).** Process boundary and optional `AutoMTLS` between host and plugin (`client.go:229-250`); no sandbox, filesystem or network policy of its own. Isolation beyond the process boundary is the embedder's job; in OMP2 terms that is the sandbox profile built in `crates/envd/src/exthost/spawn.rs:553-577`.
- **Lifecycle (X06).** `StartTimeout` bounds the wait for the handshake (`client.go:192-194, 398, 825-831`); `Kill()` ends the subprocess, waits for goroutines and removes the socket directory (`client.go:492-520`); `Reattach` can reconnect to an already running plugin (`client.go:299`); plugins are launched on demand by the embedder, so laziness is a host choice.
- **Health (X07).** For gRPC plugins the server registers the standard `grpc.health.v1` service and a controller service, and the client exposes `Ping()` through a health check (`grpc_server.go:78-93`, `grpc_client.go:127-129`). Contrast with OMP2, where no periodic liveness probe was found (`omp2-extensions.md` X07), crash detection comes from CONTROL EOF, and hang bounding from the cancel ladder.
- **Not present (X02, X03, X08, X09, X10).** No manifest or capability table (the plugin set is a Go map in the host), no registry or distribution, no upgrade or rollback, no per-platform artifact handling, no dependency declarations (searched the top-level `*.go` files and `docs/` by name).
- **Licence.** MPL-2.0 is file-level copyleft; no code was copied.
- **Lesson for OMP2.** go-plugin is the closest published precedent for what OMP2 already does: subprocess, stdout or fd handshake carrying protocol version, a negotiated application version, kill and timeout, and an optional binary checksum. OMP2's differences are a stronger boundary (inherited descriptor instead of a loopback TCP or Unix port, `spawn.rs:545-646`), a sandbox, and a signed supply chain. Two ideas it has and OMP2 lacks are version negotiation across a set (`VersionedPlugins`; OMP2 admits exactly one `API_LEVELS = {1}`) and a standard health service (cards EXT-04 and EXT-06).

## 7. bytecodealliance/wasmtime @ b738a89 (Apache-2.0)

Read: top-level layout, `crates/environ/src/component.rs:18-40` and `fact.rs:1-20` (Canonical ABI constants and fused adapters), `crates/wasmtime/src/runtime/limits.rs:30-60` (`ResourceLimiter`), `config.rs:652, 797` (fuel, epoch interruption), `crates/wasmtime/src/runtime/component/mod.rs:1-9`, `crates/c-api/README.md`, `docs/WASI-capabilities.md`. Component Model semantics beyond those lines are documentation-level (`component-model.bytecodealliance.org`, `WIT.md` linked from the READMEs); not re-derived here.

- **What it is (X01).** A WebAssembly runtime library with a Component Model embedding API (`crates/wasmtime/src/runtime/component/mod.rs:1-9`), a `bindgen!` macro that generates host bindings from WIT (`crates/component-macro/src/lib.rs:51`), WASI crates (`crates/wasi*`), and a C and C++ embedding API (`crates/c-api`). Embedded into a Rust host this adds the whole engine and its compiler stack (the repository lists `cranelift`, `winch` and `pulley` at top level); the size and startup cost for OMP2 are **not measured** (plan in EXT-10).
- **Canonical ABI is not the C ABI.** The Canonical ABI is the specified lowering and lifting of component-level values to core Wasm values and linear memory. Wasmtime encodes it as constants and compiled trampolines: functions take at most `MAX_FLAT_PARAMS = 16` flat parameters and return at most `MAX_FLAT_RESULTS = 1` flat result, beyond which values travel through the callee's linear memory (`crates/environ/src/component.rs:21-34`); calls between components go through generated "fused adapter" trampolines emitted as core Wasm (`crates/environ/src/fact.rs:1-13`). No native pointer crosses a component boundary. Wasmtime's *C API* is a different thing: an embedding interface for C hosts to drive the engine, not the guest-to-host value ABI (`crates/c-api/README.md`).
- **Isolation and limits (X05, X06).** Guests run in linear memory with host-controlled imports. The embedder can cap memory growth through `ResourceLimiter` (`limits.rs:30-60`) and bound execution with fuel and epoch interruption (`config.rs:652, 797`), so a runaway guest can be interrupted without killing the host process. WASI is capability based by design (`docs/WASI-capabilities.md`, which points at the WASI subgroup document; not read).
- **Not present.** Registry, signature verification of components, health reporting, rollback, per-platform artifacts: not part of the runtime. The repository's `supply-chain/` directory concerns Wasmtime's own Cargo dependencies, not extension distribution.
- **Lesson for OMP2.** Wasm components are the only option that is both language-neutral and memory-isolated in-process. They would add a second runtime, a second sandbox, a second dependency graph and a second packaging format next to the Python host, which is why they are `Requires ADR reconsideration` (EXT-10). A candidate fit, if the owner ever opens the question, is small deterministic logic with no ecosystem needs (parsers, scorers, request translators), not a general extension language.

## 8. bytecodealliance/wit-bindgen @ e3b53be (Apache-2.0 with LLVM exception)

Read: `README.md` opening, `crates/` listing, `crates/guest-rust/NATIVE.md`, `crates/guest-rust/src/rt/mod.rs:112-135`, `crates/core/src/abi.rs:1-20`.

- **What it is (X01, X02).** "A suite of bindings generators for languages that are compiled to WebAssembly and use the component model", driven by `*.wit` files that "specify imports, exports" (README, "About"). Generators exist for C, C++, C#, D, Go, Rust and MoonBit (`crates/` listing). It is a build-time tool for guests; it contains no runtime or registry.
- **Canonical ABI, guest half.** The Rust guest crate "only implements the **guest** half of the Component Model Canonical ABI" (`crates/guest-rust/NATIVE.md:3-6`); `crates/core/src/abi.rs` lowers WIT types to flat Wasm signatures (`WasmSignature`, `FlatTypes`). On Wasm targets the generated module exports `cabi_realloc` as a Wasm export (`crates/guest-rust/src/rt/mod.rs:124-135`).
- **Native targets blur the line.** The same crate can emit native objects: "executing native guest code (for example as a `cdylib` plugin loaded with `dlopen` ...) requires a separate native host runtime", and on non-Wasm targets component export names are encoded into valid linker symbols (`NATIVE.md:3-8, 16-29`). Consequence for this research: the Canonical ABI can be carried over a C shared-library boundary, but then the isolation that makes Wasm attractive is gone and the interface is a C symbol table again. Only the Wasm form is ABI-independent in the owner's sense. The native `cdylib` form is covered by EXT-09 (rejected).
- **Not present (X03 to X10).** No registry, signatures, health, rollback or dependency resolution; those belong to the host and to the component registries outside this repository (not read).
- **Lesson for OMP2.** If a Wasm option were ever pursued, `wit-bindgen` would be the guest-side tool and WIT the contract language, replacing OMP2's per-boundary protobuf and JSON frame definitions with one interface description. That replacement is not justified by evidence collected here.
