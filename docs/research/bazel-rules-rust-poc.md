## 1. Result in one paragraph

**The PoC builds.** It uses bzlmod, `rules_rust` 0.74.0 and `crate_universe`, reading the
workspace `Cargo.toml` and `Cargo.lock`. The toolchain is the pinned `nightly-2026-08-08`.
The subset is four crates:
- `omp-core`;
- `omp-vocab`;
- `omp-macros`, a proc-macro;
- `omp-proto`, whose `build.rs` runs protox and tonic-prost-build.

All 21 Bazel test targets pass, doctests included.

**One nightly feature is blocked: Cranelift.** The workspace builds its own crates with Cranelift
in the dev profile. Under `rules_rust` that fails, because the toolchain it downloads has no
`codegen-backends` directory (§4).

**What Bazel wins:**
- **No-op builds:** 0.9 s against Cargo's 5.2 s.
- **Unchanged test reruns:** 0.6 s against 26.7 s, because Bazel caches test results.
- **Cross-worktree reuse:** 856 of 856 actions were cache hits. That took a different worktree from
  137 s to 37 s.

**What Bazel loses:**
- **Clean builds:** 167 s against 67 s (median).
- **Incremental builds:** after a one-line `omp-core` edit, roughly a tie, 20.0 s against 17.6 s.
- **First test run:** 110 s against 70 s.

**Recommendation: no-go for adoption now. Conditional for any further Bazel work** (§8).

### Setup decisions that the evidence forced

1. **Nightly channel flag.** rules_rust puts nightly toolchains behind
   `@rules_rust//rust/toolchain/channel`, whose default is `stable`. Without
   `--@rules_rust//rust/toolchain/channel=nightly`, no toolchain matches. (V:
   `rust/private/repositories.bzl` `channel_target_settings`;
   `rust/toolchain/channel/BUILD.bazel`.)
2. **The nightly date has no built-in hash.** 0.74.0's `known_shas.bzl` lists `2026-07-16` and
   `2026-08-20`, but not `2026-08-08` (V). The first fetch was therefore unpinned. Bazel then printed
   the reproducible sha256s, which are now recorded in `MODULE.bazel`. The 0.74.0 default nightly is
   `2026-08-20` (`DEFAULT_NIGHTLY_ISO_DATE`, V).
3. **Host tools on nightly.** `crate_universe` runs `cargo` while it splices the workspace. The
   repo's `.cargo/config.toml` uses `[unstable]` keys and a `codegen-backend` profile key, so the
   host tools were pinned to the same nightly. [INFERENCE: stable host cargo would reject these.
   This was not tested.]
4. **Every workspace member's manifest must be listed** in `crate.from_cargo(manifests = …)`,
   because the root `Cargo.toml` uses `members = ["crates/*"]`. Members without a `BUILD.bazel` are
   exported from the root package.
5. **`codegen_units` trap.** This is the largest finding about the setup itself.
   - The first build used `--@rules_rust//rust/settings:codegen_units=256` and took **1373.6 s**
     (critical path 764.3 s, 994 processes).
   - Cause: rules_rust attaches a CPU `resource_set` equal to the unit count to every rustc action.
     The table is capped at 64 entries (`rust/private/rustc_resource_set.bzl`
     `get_rustc_resource_set`, V). On a 10-CPU host this serializes rustc.
   - Fix: pass `-Ccodegen-units=256` as a plain `extra_rustc_flag`, and enable
     `pipelined_compilation`, which defaults to False (V, `rust/settings/settings.bzl`).
   - After the fix the same clean build took 200.2 s (critical path 124.2 s, 1209 processes).
6. **First-party metadata does not come from Cargo.** `crate_universe` renders third-party crates.
   For first-party crates, each BUILD file had to restate by hand:
   - `crate_features`: `schemars` for `omp-core` and `tonic` for `omp-proto`. They come from the
     root `[workspace.dependencies]` specs.
   - `version`: needed for `CARGO_PKG_VERSION` in `crates/core/src/lib.rs:14`.
   - `edition`.
   - the `data` inputs for `build.rs`.
7. **Workspace `[lints]` are not applied.** The `omp-core` build printed 22
   `mismatched_lifetime_syntaxes` warnings ("hiding a lifetime that's elided elsewhere"). The
   workspace allows that lint (`Cargo.toml:332`). rules_rust has `extract_cargo_lints` plus
   `lint_config` to close this gap. The PoC did not wire them (V, `cargo/extract_cargo_lints.bzl`).

### Cross-worktree cache (the PoC's main question)

Setup:
- a second worktree of the same commit `d133d2e429`;
- a fresh `--output_base`;
- a shared `--disk_cache` (OBSERVED).

| Step | Wall | Processes | Load before |
|---|---|---|---|
| A: worktree 1, after `bazel clean`, fills the disk cache | 137.0 s | 856 darwin-sandbox, 353 internal | 72.3 |
| B: worktree 2, **new output_base**, reads the disk cache | 37.0 s | **856 disk cache hit**, 353 internal | 91.2 |
| B again, after `bazel clean` (repositories kept) | 5.3 s | **856 disk cache hit** | 68.8 |

- The disk cache held **660 MB** for this subset.
- The hit rate was **100%** for an identical tree under an identical configuration.
- Most of B's 37 s is per-output-base repository setup: the toolchain extract and crate splicing.
  [INFERENCE] The 5.3 s rerun removes that cost.
- Cargo has no content-addressed equivalent. Its nearest substitute is one shared
  `CARGO_TARGET_DIR` across worktrees, which the repo already anticipates (`crates/proto/build.rs`
  comment on shared target dirs). sccache gave mixed results
  (`docs/audits/sccache-mac-measurement.md`).

### Why Bazel's clean build is slower here ([INFERENCE] unless marked)

- **Exec configuration.** Proc-macros, build scripts and their dependencies build in Bazel's
  `opt-exec` configuration (OBSERVED: `bazel-out/darwin_arm64-opt-exec` in the action lines). That
  means optimized builds, and a second copy of `omp-core` "[for tool]" because `omp-macros` depends
  on it. Cargo builds build-time dependencies at opt-level 0.
- **Bazel's own tools.** About 20 s of the critical path in the profile is rules_rust tooling:
  `process_wrapper`, `cargo_toml_variable_extractor`, and the `_bs_` build-script runners (OBSERVED).
- **Sandboxing.** Every action runs under `darwin-sandbox` (OBSERVED), which adds setup cost per
  action.
- **Cargo-only flags are absent.** `embed-metadata=false`, `hint-mostly-unused` and the per-package
  `opt-level` overrides are Cargo profile keys. They are not mirrored.
- **Backends differ.** Cargo's dev build compiles workspace members with Cranelift. Bazel uses LLVM
  everywhere (§4). This is not an apples-to-apples comparison, and it favours Cargo on member
  crates.

The `omp-py` requirements, read from `crates/py/build.rs` and `crates/py/scripts/fetch-python.sh`
([INFERENCE] about the Bazel shape):
1. **A hermetic repository rule for the CPython tree.** It must replace the networked
   `fetch-python.sh`, which uses curl, zstd and uv and builds `stdlib.bin`, `PYTHON.json` and
   `pyo3-config.txt`. It needs:
   - an `http_archive` per python-build-standalone target, with sha256;
   - a step that runs the vendored interpreter to produce `stdlib.bin` and the bundled packages.

   There is one tree for debug and one for release, so a `select` on the compilation mode is
   needed.
2. **`pyo3-ffi` and `pyo3-build-config`** read `PYO3_CONFIG_FILE` before `omp-py`'s own script.
   Each needs a `crate.annotation(build_script_env = {"PYO3_CONFIG_FILE": "$(execpath …)"},
   build_script_data = [...])`. `AGENTS.md` ("Embedded Python") says that without it, pyo3 silently
   links a host Python.
3. **`omp-py/build.rs` leaves Bazel's declared-input model.** It:
   - emits `rustc-link-search` to an absolute vendor path;
   - emits `rustc-env=OMP_STDLIB_BLOB=<absolute vendor path>` for `include_bytes!` (lines 107, 206);
   - reads `../tools/url-vocab.json` from outside its package (line 133);
   - spawns the vendored `python3.14t` (lines 184-203).

   Under the sandbox, every one of these paths must be a declared input. The absolute paths must
   become execroot-relative.
4. **Consumer binaries** need the final link flags `--ld-path=<shim>` and `-Wl,-export_dynamic`
   (`AGENTS.md` "Embedded Python"). Release builds need Homebrew LLD 22 for LTO bitcode.

## 7. What the numbers say ([INFERENCE])

- The one property the PoC was asked about holds: **per-action, content-addressed reuse across
  worktrees works (100% hits)**. That is the gap that sccache and BuildBuddy cannot fill for Cargo.
- Bazel's big wins are on no-change paths: no-op, cached tests and a warm cache in another
  worktree. On the edit-compile loop that developers and agents actually run, it is not faster.
  It is slower on cold builds and on the first test run. Part of that is structural (exec-config
  optimized builds and duplicate first-party builds). Part comes from Cranelift being unavailable.
- Making the wins real for omp needs three things:
  - the CPython closure, which most of the workspace links through `omp-py`;
  - a cache store that does not create a hard BuildBuddy dependency;
  - a second build graph kept in step with Cargo.

  None of these exists today.

## 8. Recommendation

**No-go** for adopting Bazel, even partially for leaf crates. This matches the owner constraint in
ADR 0040.

**Conditional go** for any further Bazel work. Revisit only if all of the following hold:
1. **Cranelift is solved.** Either rules_rust can load the `rustc-codegen-cranelift-preview`
   component (rules_rust#2555, or a custom toolchain repository), or the owner accepts LLVM-only
   dev builds.
2. **A CPython rule is prototyped** for `omp-py` and passes the existing `omp-py` tests in the
   sandbox (§5 items 1–3).
3. **A cache backend exists that is not a hard dependency.** Either a local or self-hosted REAPI
   cache, or BuildBuddy behind a flag, as the R2 constraint requires.
4. **Phase B Cargo baselines show the need.** They must show that cached test reruns or
   cross-worktree rebuilds are a dominant cost. The measurements here suggest Cargo-native options
   should be tried first: a shared `CARGO_TARGET_DIR` across worktrees, and nextest
   change-detection or selective testing (prior research item 44, Phase F).
